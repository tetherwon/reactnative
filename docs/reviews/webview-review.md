# WebView startup / logged-out review (2026-09-11)

Scope: `src/app/index.tsx`, `src/hooks/useWebViewAuth.ts`, `src/app/+native-intent.tsx`, `src/lib/externalLinks.ts`, and associated tests. Compared screen logic with the pre-refactor main version; the confirmed load-state defects predate PR #10. This review does not prove a physical device can launch the native binary.

| File | Review and result |
| --- | --- |
| `src/app/index.tsx` | Confirmed: `onLoadEnd` marked failed documents ready, so subsequent push/auth injections could be consumed by an error document. Later successful loads did not clear the app's error overlay. Fixed readiness invalidation on every load start and failure, preserving queued work until success. |
| `src/app/index.tsx` | Confirmed missing recovery: no time limit when native loading callbacks never arrive, no main-frame HTTP failure handler, and no Android renderer-death handler. Added a 30-second mount/navigation watchdog, an error screen for these failure events, and explicit retry that creates a fresh native WebView. iOS termination now uses the same recovery instead of potentially repeated automatic reloads. Timer is cleaned on completion, error and unmount. |
| `src/hooks/useWebViewAuth.ts` | An ordinary logged-out launch has no `code`/`state`, so no exchange or token injection runs. OAuth state is independent of whether the screen can render. Deferred tokens wait for readiness and own origin. Existing JS injection rechecks exact `location.origin`. Added a no-credentials regression test. |
| `src/app/+native-intent.tsx` | Invalid URL parsing returns `/`, and callback routing forwards code/state only; raw bearer tokens are not forwarded. No unconditional logged-out startup blocker found. |
| `src/lib/externalLinks.ts` | Home origin and login provider URLs are allowed through the expected paths. Native OAuth interception checks exact origin and known start path; normal `/` loading is not intercepted. External protocol failures are caught. Security follow-up: `isAppOrigin` uses host parsing that strips any numeric port rather than exact URL origin, so a nonstandard port is treated as own origin by this helper; JS token/bridge injection separately rechecks exact origin. No change made to this unrelated origin-policy behavior in this startup fix. |
| `tests/webview-load.test.cjs` | Six screen-level VM tests: ordinary logged-out rendering, failed-document queue preservation and recovery, absent callbacks plus timeout/retry/cleanup, HTTP failure, Android renderer failure, iOS process termination. These test JavaScript callback behavior, not an actual native WebView or network. |
| `tests/webview-hooks.test.cjs` | Existing PKCE cold-start/token-origin and native bridge checks retained, plus a test showing no credential exchange or token injection when logged out. |

Validation: the readiness regression failed against the pre-fix screen (`true !== false` after an error followed by load end), then passed after the fix. New six screen tests and TypeScript check passed. Native dependency source confirms that `onHttpError` is emitted only for main-frame responses on Android (`RNCWebViewClient.java`) and iOS (`RNCWebViewImpl.m`), so an image or ad request failure will not trigger this handler.

Remaining verification: cold-install launches on actual Android/iOS with no account, real server HTML/JS execution, slow/offline recovery, then OAuth callback and push navigation. Thirty seconds is the intentional full-document load timeout; a very slow connection can reach the retry screen. The underlying native crash, if any, still needs crash logs and investigation of startup modules outside this review's scope.
